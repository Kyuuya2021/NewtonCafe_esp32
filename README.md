## プロジェクト概要

### 何を解決するか

ネットカフェのコワーキングスペースにおいて、利用者の**集中度を非侵襲的にリアルタイム計測**し、適切な休憩促進と作業効率の可視化を実現する。

### 技術的アプローチ

カメラを使わず、**WiFi電波のCSI（Channel State Information）** を分析することで、プライバシーを侵害せずに人体の動き・呼吸・心拍を検出する。Gemini APIによる手元カメラ解析と組み合わせて、より精度の高い集中度スコアを算出する。

### ビジネスモデル

```
各店舗にハードウェアパッケージを導入
    ↓
月額SaaSとして集中度管理機能を提供
    ↓
利用者の体験向上 → ニュートンカフェのリピート率向上
```

## 通信アーキテクチャ

### データフロー詳細

```
【Step 1: CSIデータ取得】
ESP32（100Hz）
  → WiFi 2.4GHz（UDP）
  → モバイルルーター（L2スイッチとして動作）
  → Mini PC port 5005

【Step 2: データ処理】
RuView（Docker）
  → CSI信号処理（振幅・位相解析）
  → 骨格推定 / 心拍・呼吸抽出
  → REST API: http://localhost:3000/api/v1/

【Step 3: 集中度算出】
Concentration Agent（Python）
  → RuView APIをポーリング（1秒ごと）
  → 集中度スコア算出（0〜100）
  → クラウドAPIへ送信（HTTPS）

【Step 4: クラウド統合】
Node.js バックエンド
  → ESP32データ + Geminiカメラデータを統合
  → 最終集中度スコアを計算
  → WebSocket で フロントエンドにプッシュ

【Step 5: 表示】
Next.js フロントエンド
  → 部屋モニター: 在室者全員のスコアをリアルタイム表示
  → 個人ダッシュボード: 自分のスコア・グラフ
  → 通知: 集中度が低下したら休憩を促す
```

### ネットワーク構成

```
インターネット
     │
     │ (ネカフェの既存回線 or モバイル回線)
     │
Mini PC ─────────────────────────────────────
     │                                       ↑ HTTPS
     │ WiFi or 有線LAN（インターネット用）    クラウド
     │
     └── モバイルルーター（ESP32専用）
              │
              │ WiFi 2.4GHz（LAN内通信 / インターネット不要）
              │
         ┌────┴────┐
      ESP32-1  ESP32-2  ESP32-3  ESP32-4
```

**重要**: ESP32 ↔ Mini PC間の通信は完全にLAN内で完結。モバイルデータを消費しない。

## 集中度スコアの算出ロジック

### 入力データ

| データソース | 取得方法 | 更新頻度 |
|------------|---------|---------|
| 体動量（動き）| ESP32 CSI振幅変化 | 100Hz |
| 呼吸数 | CSI位相変化（0.1〜0.5Hz成分） | 10Hz |
| 心拍数 | CSI位相変化（1〜2Hz成分） | 10Hz |
| 姿勢推定 | RuView骨格推定 | 25Hz |
| 手元画像 | Gemini API解析 | 30秒ごと |

### スコア算出式（暫定）

```python
def calculate_concentration_score(motion, breathing, heartrate, posture, camera):
    """
    集中度スコア算出（0〜100）
    
    Parameters
    ----------
    motion      : float  体動量（小さいほど集中）
    breathing   : float  呼吸数/分（正常: 12〜20）
    heartrate   : float  心拍数/分（正常: 60〜100）
    posture     : float  姿勢スコア（0〜1）
    camera      : float  カメラ解析スコア（0〜1）
    """
    
    # 体動スコア（動きが少ないほど高スコア）
    motion_score = max(0, 100 - motion * 10)
    
    # 呼吸スコア（正常範囲で高スコア）
    breathing_score = 100 if 12 <= breathing <= 20 else 60
    
    # 心拍スコア（安定しているほど高スコア）
    heartrate_score = 100 if 60 <= heartrate <= 100 else 50
    
    # 重み付け統合
    score = (
        motion_score    * 0.35 +  # 体動: 35%
        posture         * 0.25 +  # 姿勢: 25%
        camera          * 0.25 +  # カメラ: 25%
        breathing_score * 0.10 +  # 呼吸: 10%
        heartrate_score * 0.05    # 心拍: 5%
    )
    
    return round(score, 1)
```

### 集中度レベル定義

| スコア | レベル | 表示色 | アクション |
|--------|--------|--------|----------|
| 80〜100 | 深集中 | 🟢 緑 | なし |
| 60〜79 | 集中 | 🔵 青 | なし |
| 40〜59 | やや散漫 | 🟡 黄 | 軽い通知 |
| 0〜39 | 要休憩 | 🔴 赤 | 休憩促進通知 |

## セットアップ手順

### 開発者向け初期セットアップ

#### 1. ファームウェアのビルド（Mac推奨）

```bash
# リポジトリのクローン
git clone https://github.com/ruvnet/RuView.git
cd RuView

# ファームウェアのビルド
cd firmware/esp32-csi-node
idf.py build

# 重要な設定変更
# sdkconfig: CONFIG_EDGE_TIER=0
# edge_processing.c: vTaskDelay(pdMS_TO_TICKS(5))
# stream_sender.c: setsockopt SO_SNDBUF=4096
```

#### 2. ESP32へのファームウェア書き込み（Windows）

```powershell
cd C:\Users\nagano\RuView

# ファームウェア書き込み
py -m esptool --chip esp32s3 -p COM3 -b 460800 write-flash `
  --flash-mode dio --flash-size 8MB --flash-freq 80m `
  0x0 firmware\esp32-csi-node\bootloader.bin `
  0x8000 firmware\esp32-csi-node\partition-table.bin `
  0x20000 firmware\esp32-csi-node\esp32-csi-node.bin
```

#### 3. WiFi設定の書き込み（4台分）

```powershell
# Node 1〜4 を順番に実行
py firmware/esp32-csi-node/provision.py `
  --port COM3 `
  --ssid "YOUR_WIFI_SSID" `
  --password "YOUR_PASSWORD" `
  --target-ip 192.168.X.X `
  --target-port 5005 `
  --edge-tier 0 `
  --node-id 1
```

#### 4. Dockerサーバーの起動（Windows）

```powershell
cd C:\Users\nagano\RuView\docker
docker compose start
```

#### 5. 動作確認

```
ブラウザで http://localhost:3000/ui/index.html を開く
→ Data Source: ESP32 と表示されれば成功
→ Hardware タブで Active TX: 3/3, Active RX: 6/6 を確認
```

## 既知の問題・制約

### RuViewのTraining機能

RuViewのDockerイメージ内でTraining機能が未完全実装の状態。`Training started`のログは出るがモデルファイルが生成されない。

**対応方針**: RuViewのTraining機能に依存せず、APIから取得したデータを独自Pythonスクリプトで処理して集中度スコアを算出する。

### WindowsのDockerとUDP通信

WindowsのDockerはUDPポートの転送に制限があり、コンテナ再起動のタイミングによってはESP32からのデータを受信できないことがある。

**対応方針**: `SENSING_BIND_ADDR=0.0.0.0`の設定で回避済み。

### IPアドレスの変動

DHCPによりMini PCのIPアドレスが変動する場合がある。

**対応方針**: セットアップ時にルーターの管理画面でMACアドレスバインディングを行い、IPアドレスを固定する。

### ネットワーク要件

- ネカフェの既存WiFiはデバイス間通信をブロック（Client Isolation）しているため使用不可
- ネカフェの有線LANにTP-Linkを接続するとDHCP競合でネットワーク全停止が発生した実績あり
- **結論**: 店舗ごとに独立したモバイルルーターを持ち込む構成が必須
